# 浏览器、WebRTC、IPv6

## 明确哪一个浏览器

记录 Chrome/Safari/Edge/独立浏览器环境以及 Profile。Claude Desktop 的登录窗口、系统 OAuth（跳转到身份服务完成登录的流程）与日常浏览器可能走不同路线，应分别检查。不要用另一浏览器的好结果证明目标已通过。

普通浏览器使用系统代理时，确认它确实跟随 Shadowrocket；独立环境若支持显式 HTTP 代理，可以绑定现场已验证的回环入口。共享本机端口仍会跟随 Shadowrocket 选中节点与规则，不等于独立固定出口。

历史专用代理方案曾对单个浏览器使用独立本机入口，并在停止该服务后确认浏览器报代理连接失败。此经验不能直接证明共享入口也有相同隔离。用户要求独立出口时才设计专用客户端，另做验证；不自动部署 Xray、服务端或更改任何已有节点。

## DNS 与浏览器自身的覆写

检查浏览器“安全 DNS”、扩展、企业策略和启动方式。可以让浏览器交由已验证的 Shadowrocket 解析，也可保留经代理且无系统回退的显式 DoH；关键是实际请求路径。不要看到浏览器勾选“安全 DNS”就宣告无泄露。

在同一个 Profile 运行 https://browserleaks.com/dns 两轮，记录预期与观察到的解析服务归属。多个递归解析器地址/地理位置不自动等于泄露；解析器 IP 不需要与代理出口一致。区分本地运营商解析、代理出口侧解析及测试站数据库标注误差。仅页面显示通过而缺连接证据时保留相应局限。

## WebRTC（浏览器音视频通信，可产生独立连接）

Chromium 支持 `disable_non_proxied_udp`，用于限制不经过代理的 UDP。实施途径可以是目标浏览器自身设置、受支持策略或可信扩展；先确认作用范围和实际生效状态。该选项不等于禁用整个 WebRTC，也不保证所有浏览器/版本绝无泄露。

- 不依靠伪造或替换显示 IP 代替真实路由限制。
- 不盲改所有浏览器的全局策略；策略可能被组织管理或扩展覆盖，必须回读。
- Firefox/Safari 不照抄 Chromium 字段；查当前产品实际支持的设置，没有可靠控制时使用目标环境实测并标记限制。
- 实际浏览器访问 https://browserleaks.com/webrtc，记录候选地址和是否出现本地运营商公网 IP。私网地址或 mDNS 名称与公网地址泄露分开解释。
- 页面 “No Leak” 是当前配置下的一次测试结果，需确认检测实际运行成功；脚本被扩展阻断、测试没有完成都不能算通过。有语音需求时验证音视频可用性。

## IPv4/IPv6

在目标浏览器检查 IPv4 与双栈路径，例如 https://api.ipify.org 与 https://api64.ipify.org，再结合当前设备/节点的网络事实解释。双栈地址返回 IPv4 不能证明 IPv6 路径已经验收；需要另用当前可用的 IPv6-only 检测地址在同一浏览器验证，确认检测实际发起且完成。仅终端强制 IPv6 请求不能替代浏览器证据。

只有已经确认环境本身没有 IPv6 能力时才记为“不适用”；原因不明的 IPv6 超时、测试脚本受阻或未完成记为“未测/待定位”，不能写成“无泄露通过”。检测 URL 的结果只用于对应路径，不是所有域名的保证。

三种结果区别对待：

- 本地运营商公网 IPv6 出现在预期代理的请求：旁路嫌疑，查浏览器/客户端/路由。
- 代理节点的 IPv6 出现：可能仍经代理，但没有达到“固定单一 IPv4”的要求。
- DNS 列表中的解析器 IPv6：不能据此认定本机 IPv6 泄露。

不默认关闭全系统 IPv6；限定到目标应用/配置，先测试。仅客户端选择 IPv4 不保证远端节点最终以 IPv4 访问目标。需要远端配置才能解决时说明边界，本技能不进入服务器操作。

## 失败时停止联网的测试

优先临时测试 Profile/专用代理进程，不停止整机 Shadowrocket。对测试环境使用不可达代理端口，可以验证“显式代理不可用时浏览器是否失败”，但不能代替真实上游故障或断线后的验证。

针对专用代理的实际停启需有恢复方法和可接受窗口，先保留当前操作通道。页面应连接失败，不应悄悄改用本机网络；恢复后确认预期出口。普通浏览器、独立环境、系统认证窗口分别报告覆盖范围。
